P4Guard: a self-enforcing Perforce CI platform

A local Perforce Helix Core server that rejects bad changelists at p4 submit, kicks off its own CI, and reports on itself — built to prove the front-end integration skillset, not just describe it.

Most portfolio projects that claim "CI/CD experience" are a YAML file and a screenshot. This one is a real, working system: a genuine local Perforce Helix Core server, provisioned entirely from spec files, with Python triggers that actually reject bad submits, a CI orchestrator that actually runs, and a dashboard built from actual run history. Everything in this post is something you can run yourself and watch happen — there's a link to exactly how, at the bottom.

Perforce in 90 seconds

If you've never touched Perforce, five ideas cover almost everything below. If you have, skip ahead to the problem.

  • Depot — the central repository. Everything lives under one root, like //frontend_asic/.
  • Stream — a branch, but Perforce also knows its relationship to its parent (mainline, development, or release) and can enforce that branching model for you.
  • Workspace — your local checkout, defined by a spec that maps depot paths to a local folder.
  • Changelist — a numbered batch of pending edits. You p4 edit a file, change it, then p4 submit — submitting and committing are the same moment.
  • Trigger — a script the server runs automatically at a point in a command's lifecycle, able to reject the command outright. This is the mechanism the whole project is built around.

The problem

Several IP teams — SerDes, MAC, PCIe, in this project's stand-in chip — commit RTL into one shared depot. Someone has to guarantee that a broken or badly-styled commit never reaches the stream everyone else builds on, that every commit runs through lint/synthesis/equivalence/simulation without a human remembering to kick it off, that a broken build gets noticed in minutes instead of days, and that a release drop is an unambiguous, reproducible snapshot rather than "whichever changelist someone thinks is stable." Perforce gives you the primitives — triggers, streams, labels — but none of that policy enforcement exists until someone builds it on top. That layer is what this project is.

The architecture

The distinction between step 1 and step 2 above is the single trickiest part of the whole project. Perforce actually offers three separate trigger points around a submit: change-submit fires before any file content is transferred to the server, change-content fires once content has been transferred but before it's committed — the only point where a trigger can inspect what's about to land — and change-commit fires after it's durably committed. The policy check (does the description reference a ticket?) only needs the description, so it runs at change-submit, the cheapest possible rejection point. The lint check needs to see the actual file content, so it has to run at change-content — registering it as change-submit instead looks correct, runs without error, and silently never catches anything, because the content it's trying to read doesn't exist yet at that point in the lifecycle. That's a real bug this project hit and fixed, not a hypothetical.

What I built

Six pieces, each doing real work rather than standing in for it:

  • Streams & protections — the topology above, provisioned from checked-in spec files rather than clicked together, so the whole depot is reproducible from scratch on any machine.
  • Three pre-submit gates — ticket-reference policy, RTL lint (naming convention, incomplete case, a latch-inference heuristic), and a release-stream sign-off requirement — all real Perforce triggers, all capable of actually rejecting a submit.
  • A post-submit trigger that inspects which IP block a changelist touched and launches a scoped CI run, detached, so it never adds latency to the submit itself.
  • An EDA-flow orchestrator reading a YAML pipeline spec and running lint → synthesis → equivalence → simulation. The licensed tools this would normally wrap — SpyGlass, Design Compiler, Conformal, Xcelium — aren't available outside a company environment, so each stage is a wrapper matching that tool's real CLI shape and report format, doing genuine (if simplified) analysis on the RTL text — not a fabricated pass/fail. The simulation stage goes one step further: if Icarus Verilog is installed, it compiles and runs the testbench for real.
  • A compute-farm simulation — bsub/bjobs/bqueues-shaped local job queue with real slot limits, so every pipeline stage genuinely queues and the farm-utilization numbers are computed, not invented.
  • Reporting — a dashboard built from real run history, and a Slack notifier that posts (or safely dry-runs, without a real webhook) after every run.

The honest line to draw: the Perforce server, its streams/triggers/protections, and every submit/login/label operation are completely real. The EDA tools are necessarily mocked — but structured so that swapping a mock for the real licensed tool is a one-line change to the command being run, not a rewrite of the orchestration, farm integration, or trigger logic around it.

Try it yourself

The full step-by-step guide — prerequisites, bootstrap, and a live walkthrough of the demo (a lint violation getting rejected, fixed, accepted, and auto-triggering CI, in that order) — is in the repository's README. In short:

python -m venv .venv && .venv/Scripts/pip install -r requirements.txt
pytest tests -q

bash scripts/bootstrap_p4_server.sh   # stands up a dedicated local p4d
bash scripts/run_demo.sh              # live reject/accept demo, end to end

Both scripts print exactly what they're doing at each step, so you can watch a real submit get rejected and then accepted rather than taking a README's word for it.
