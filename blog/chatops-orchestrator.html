ChatOps Workspace Orchestrator

Kicking off a build shouldn't require remembering a hostname, opening a terminal, and typing a command you run twice a month. This is a chat command surface for the handful of workspace operations that are small enough not to deserve that much ceremony.

The friction this removes

Most of the operations in this project — syncing a workspace, kicking off a farm build, checking whether a job is still running — are individually trivial but collectively annoying because each one normally means: SSH into the right machine, remember the exact command and its flags, run it, then remember to go check on it later. None of that is hard. All of it is friction that adds up specifically for the small, frequent tasks that don't justify opening a full terminal session — which is exactly the case a chat command is good at.

What it actually is

A small bot living in a Slack channel, wired to the same workspace and farm tooling the rest of this project uses. An engineer types something like @bot sync frontend_dev and kick a lint build, and the bot parses that into a specific action, executes it against the actual workspace/farm APIs, and posts the result back in the same thread — including a follow-up message when a long-running build finishes, so nobody has to remember to go check.

Why a whitelist, not general command execution

The tempting version of this project lets the LLM translate any natural-language request into an arbitrary shell command. That's also the version that's one ambiguous phrasing away from something destructive running against a real workspace. Instead, the bot maps natural language onto a small, explicit set of pre-approved operations — sync, launch_build, job_status, and a handful of others — each with a fixed, parameterized implementation. The LLM's job is narrow: figure out which whitelisted operation was meant and extract its parameters, never to construct or execute a command directly.

Confirmation for anything with a blast radius

Even within the whitelist, not every operation is equally safe to fire on a best-guess parse. Read-only operations like checking a job's status execute immediately. Anything that changes state — a sync, a build launch — gets a one-line confirmation echoed back before it runs ("sync frontend_dev to head — confirm?"), so a misheard workspace name gets caught by the person who typed the request, in the two seconds before it would have mattered, rather than after.

Monitoring in the same surface

The part that saves the most actual time isn't the triggering — it's not having to go check back. A build kicked off through the bot posts its own completion status back into the thread it was launched from, success or failure, without the engineer needing to poll it. Combined with the hung-job detection from the release gate, a build that's stalled gets flagged in the same thread too, instead of silently sitting unfinished until someone happens to look.

Where it stops

This is deliberately not a general admin interface. It's scoped to the small set of low-risk, frequent operations that were previously worth a full terminal session only because there was no faster path — not a replacement for direct access to the workspace or farm for anything more involved.
