FCNN on FPGA: a neural network built from Verilog primitives

No neural-network IP core, no HLS. Every adder, multiplier, and neuron in this network is hand-written Verilog, synthesized down to a Zybo Z7 and driven by weights trained in TensorFlow.

Most "neural network on FPGA" projects start from a vendor IP core or an HLS toolchain that compiles C++ down to RTL. This one starts from Verilog primitives — a multiplier, an adder, a neuron built out of both, a dense layer built out of neurons — and composes upward until the composition is the network. The point wasn't to get to a working accelerator the fastest way possible; it was to actually own every stage between a trained model and a bitstream.

Bottom-up composition

The design is a fully connected neural network (FCNN) built on a Zybo Z7 board in Vivado, structured in the same order you'd draw it on a whiteboard:

  • A fixed-point multiplier and adder — the network runs in 16-bit fixed point, not float, so the first design decision was where the binary point sits and how much dynamic range that leaves for activations without saturating.
  • A neuron — a multiply-accumulate over one input vector against one weight vector, plus a bias add and activation.
  • A dense layer — neurons instantiated in parallel across the layer's width, sharing an input bus.
  • The full network — dense layers chained, each stage's output register feeding the next.

Building it this way means every stage is independently testable in isolation before it's ever composed with the next — a multiplier can be checked against known products, a single neuron against a known dot product, well before "does the whole network classify correctly" becomes the question being debugged.

Getting trained weights into hardware

The network was trained in TensorFlow at full precision, then the weights were quantized to 16-bit fixed point and extracted into a flat binary file — no retraining or fine-tuning in the fixed-point domain, just a direct cast. That binary is loaded into block RAM at synthesis/implementation time, so the hardware that comes up on the board is running the exact weights the Python model was trained to produce, just re-expressed in fixed point.

Extending it: on-chip image processing

The second half of the project pushed the same hardware into a streaming image pipeline instead of a one-shot classifier: image data streams into the FPGA line-by-line, gets convolved on-chip against the loaded kernel weights as it arrives — no full-frame buffer required before processing starts — and the result streams back out to a Python host, where OpenCV and NumPy handle final rendering and display. Doing the convolution on-chip and rendering off-chip splits the design at its natural boundary: the FPGA does the part that benefits from parallel fixed-point arithmetic, Python does the part that benefits from a mature image library.

What building it bottom-up actually taught

HLS and IP cores exist precisely because this approach is slow to build. What it buys back is that nothing is a black box: when the classifier's output didn't match the Python reference during bring-up, the bug was traceable to a specific pipeline stage rather than being "somewhere in the accelerator." That kind of traceability — being able to point at the exact register where a value diverges from spec — is the same skill this project shares with verification work more broadly.
