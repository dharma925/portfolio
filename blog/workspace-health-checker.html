Workspace Health Checker

Most workspace breakages aren't caused by a bad change — they're caused by a stale or drifted local environment that a bad change simply exposes. This gate checks the environment, not just the diff, before submit is allowed to succeed.

The P4Guard post covers policy-gate and lint-gate — two triggers that inspect what a changelist actually contains. This one is different: it inspects the state of the workspace itself, before content is even considered, because a large share of "why did my submit fail" problems trace back to something wrong with the local checkout rather than the change.

What "unhealthy" looks like

A workspace can drift from a known-good state in ways that have nothing to do with what you're about to submit:

  • A stale sync — testing against files from three days ago while the depot has since moved on, so a passing local test proves nothing about the actual target.
  • A version mismatch — a required tool or library resolved to a different version than the one the project pins, silently changing behavior.
  • A conflicted mapping — overlapping workspace views that leave a file resolving to the wrong depot path.

Every one of these produces a confusing, misleading failure that looks like it's about the change being submitted, when it's actually about the environment the change was tested in.

Where the check runs

It hooks in as an earlier stage than policy-gate in the P4Guard trigger chain — cheapest checks first, since there's no point inspecting change content from a workspace that's already known to be in a bad state. It runs a small, fast battery: sync freshness against the target stream, tool/library version resolution against the pinned manifest, and a mapping-conflict check against the workspace spec. All three are fast enough to run on every submit attempt without adding meaningful latency.

The embedded LLM's actual job

A sanity check that just prints FAIL: stale sync is only half useful — the engineer still has to know the fix is p4 sync, not something scarier. The embedded agent's job is narrow and specific: take the exact failure signature, plus the workspace's current spec, and draft the specific command that resolves it — not a general troubleshooting essay, one copy-pasteable next step. For a stale sync, that's the exact sync invocation for the affected paths. For a version mismatch, it's which pinned version to switch to and how. Keeping the agent's scope this narrow is deliberate: it's drafting a mechanical fix for a diagnosed, known category of problem, not reasoning freely about an open-ended failure.

What it actually prevents

Without this gate, a broken workspace tends to surface downstream instead of at the point of submit — as a confusing regression failure that isn't really a regression, or a merge conflict that only makes sense once someone notices the sync gap, or a version-mismatch bug that takes a while to trace back to "your tool version wasn't what the project expected." Catching it at the gate turns all three into a one-line, self-explaining rejection at the moment the engineer is already looking at their terminal, instead of a mystery someone else inherits later.
