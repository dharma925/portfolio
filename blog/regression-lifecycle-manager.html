Autonomous Regression Lifecycle Manager

A regression suite doesn't run itself — someone has to sync, launch, notice what broke, decide whether it's worth a retry, and tell the right person. This agent, built on top of the orchestrator framework, does all of it without a human in the loop.

Running a regression suite once is easy: sync a workspace, kick off the jobs, wait, read the results. Running it as a lifecycle — every night, unattended, correctly, for months — is a different problem. Each of those four steps has a failure mode a human normally catches by hand: syncs get stale, jobs die on a bad compute node, "what broke" needs judgment to separate a real bug from a flaky retry, and someone has to actually notice and act on the result before morning stand-up. This agent exists to close that loop end to end.

The four stages

  • Sync — bring every relevant workspace up to the target changelist or tag before anything launches, so a stale checkout never silently produces a stale result.
  • Launch — submit the suite to the compute farm, tracking job IDs against the state machine described in the orchestrator post so a restart never double-launches.
  • Triage — once results land, classify each failure: a known-flaky test that just needs a retry, a local/environmental issue with a mechanical fix, or a real regression that needs a person.
  • Report — dispatch a debug report scoped to what actually changed, not a wall of every result.

Selective relaunch, not full relaunch

The naive version of "retry on failure" reruns the entire suite. For a suite with a few thousand tests, that's enormously wasteful when only a handful failed. The lifecycle manager keeps a per-test result history, so a relaunch means exactly one thing: resubmit the specific failing test IDs from the specific failing run, nothing else. That distinction — relaunching a subset versus relaunching everything — is most of where the "autonomous" part earns its keep, because it's the difference between a retry costing a few compute-minutes and costing an entire farm-night.

Deciding what's safe to auto-fix

Not every failure needs a human. Some have a mechanical, known-safe fix: a stale workspace that just needs a re-sync, a license checkout that timed out and should be retried once, a test that depends on a scratch directory that wasn't cleaned up from a previous run. The agent keeps a small, explicit list of these known-safe patterns — matched against the failure signature, not guessed by the LLM — and only auto-applies a fix when the match is exact. Anything that doesn't match a known pattern gets escalated, not guessed at. That asymmetry is deliberate: false positives on "safe to auto-fix" are far more expensive than a slightly-too-conservative escalation policy.

Routing, not just reporting

A debug report that goes to one shared channel gets skimmed and ignored. The lifecycle manager maps each failing test back to the component it exercises — using ownership metadata checked into the repo alongside the test itself — and routes the report to whoever owns that component, with just the failure signature, the relevant log excerpt, and a link to the full run. The report a component owner gets is scoped to their component, not the whole suite's overnight output.

Where the off-hours angle comes from

Interactive compute and license seats are scarce during the day — everyone's iterating on their own change. They're mostly idle overnight. A lifecycle manager that only launches once everyone's synced up and waits for a human to notice results the next afternoon is leaving that idle capacity on the table. Scheduling full regression launches for the overnight window, and having triage and routing happen automatically before anyone's at their desk, means the farm and license pool are doing useful work exactly when nothing else is competing for them, and a broken build is already scoped and routed by the time someone would have gone looking for it manually.
