MACTrace: a C++ model of a CNN accelerator, before any RTL exists

Most "CNN accelerator" side projects are really just CNN inference written in C++. This one models the hardware instead — a configurable MAC array, an accumulator, an on-chip buffer — and keeps does it compute the right answer strictly separate from how many cycles does it cost, the same split a real accelerator architecture team draws before RTL exists.

Status: Phases 1–2 complete — a working functional model, real trained and quantized weights, bit-exact Python↔C++ validation, and a measured performance model. Phase 3 (multi-configuration architecture sweep) and Phase 4 (dataflow optimization) are still in progress.

Two models, kept deliberately separate

  • Functional model — does the accelerator compute the correct answer? No notion of time at all. The same role a golden reference model plays in a verification flow.
  • Performance model — given N MAC units, a buffer size, and a tiling strategy, how many cycles does this workload cost, and how well does it use the hardware? Explicitly not claimed to be RTL-cycle-accurate — a fast, documented, architecturally-informed estimate, the kind of model that lets you compare design points cheaply before committing to RTL.

Architecture

The target pipeline, and roughly how each stage maps to C++:

Four pieces do most of the work:

  • Tensor<T>

    Row-major, shape/stride-based storage — a software stand-in for what sits in an on-chip buffer, with indexing that plays the role of an address-generation unit.

  • MacArray / MacUnit

    A configurable rows×cols grid of PEs, each a multiply-accumulate plus a register — the software analogue of instantiating N identical hardware modules through a generate loop.

  • LocalBuffer<T>

    Capacity-bounded on-chip storage a tile must be staged into before compute — an SRAM capacity constraint that's actually enforced, not just commented.

  • PerfCounters

    PMU-style free-running counters — MAC ops, cycles, buffer traffic, utilization — read and reset at layer boundaries, the same pattern real performance-monitoring hardware uses.

Results — measured, not assumed

A small CNN (Conv → ReLU → MaxPool → FC) was trained on MNIST in PyTorch, post-training quantized to INT8, exported into a custom binary format, and run through the C++ model. Every number below comes from an actual run, not an estimate:

  • 96.46% float32 test accuracy, 96.43% INT8 test accuracy across 10,000 images — quantization cost almost nothing here.
  • 0 — the maximum logit difference between the C++ model and an independently-implemented NumPy reference (not a shared code path, a second implementation), across 20 test images and 10 output classes each.
  • 100% MAC utilization on the conv layer, versus 20.8% on the FC layer.
  • 11,662 estimated cycles for a full inference pass on a 4×4 MAC array.

The finding underneath those numbers: the fully-connected layer costs almost as many total cycles as the convolution layer — 5,782 versus 5,880 — despite doing roughly a quarter as much useful work per cycle on average, because mapping a single-vector FC layer onto a spatial MAC array only ever fills one of N rows. It's a concrete demonstration that adding more MAC units doesn't automatically improve throughput; utilization depends on whether the workload's shape can actually fill the array.

The cycle model, documented rather than implied

Claiming RTL-level accuracy a model doesn't have is worse than being upfront about what it approximates:

// per GEMM tile of shape (R, K) x (K, C) -> (R, C):
compute_cycles = K                                 // one MAC/cycle per active PE
load_cycles    = ceil(R*K / bw) + ceil(K*C / bw)   // sequential tile staging
tile_cycles    = load_cycles + compute_cycles

mac_utilization = mac_ops / (mac_rows * mac_cols * compute_cycles)

No pipeline stalls, no load/compute overlap, no off-chip-vs-on-chip distinction — a fast, relative model for comparing architectural configurations, the kind a team builds before RTL exists, not a substitute for RTL simulation.

Why the golden-model split matters

Checking the C++ output against an independently-implemented reference — not the same code path re-run, a second implementation — is the same discipline as comparing a DUT against a golden model in a verification testbench: if both implementations agree on every one of 200 output logits by chance, that's a much weaker claim than a maximum diff of exactly zero. Keeping functional correctness and cycle-count estimation as two separate models, checked separately, is what makes each one trustworthy on its own terms instead of one hiding the other's mistakes.
